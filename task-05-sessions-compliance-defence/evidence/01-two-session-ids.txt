## 1. Overview & Verification Goal
Prove that logging in twice for the same user creates two distinct, independent session records in SQLite, each with:
1. A cryptographically secure 256-bit random entropy token delivered only to the client in the `freshfold_session` cookie.
2. A one-way SHA-256 hash stored in the database `sessions.token_hash` column (raw tokens are NEVER persisted in SQLite).
3. Independent session IDs and independent expiry timestamps.

## 5. Cryptographic Proof: SHA-256 One-Way Hash Verification
To prove the raw session tokens in the browser cookies map 1-to-1 to the hashed database columns:

```typescript
// Verification in Node.js
const crypto = require('crypto');

const cookie1 = '365fc3c2f0863729f98d2e697375829e291c2dd24cdb35efef7f3796014af07d';
const hash1 = crypto.createHash('sha256').update(cookie1).digest('hex');
// Result: c6ff6f9045b6b5303519047696e5a4b32be98de863dcb73397258262b231a3a4
// Matches SQLite sessions row id=1 token_hash exactly: TRUE

const cookie2 = '8a92e4a609d4e4b7fcf1c59bdd868492e7c80f1725502399e65cf222b2e796f4';
const hash2 = crypto.createHash('sha256').update(cookie2).digest('hex');
// Result: 797eaf2ba4e304db90b75c3402f0ef2313098877583f5abd000c99ea6ce73673
// Matches SQLite sessions row id=2 token_hash exactly: TRUE
```

## 6. Architectural Conclusion
1. Two consecutive logins produced two completely distinct session tokens (256 bits of entropy each).
2. Storing raw tokens in SQLite is strictly avoided; an adversary reading a database backup cannot impersonate active sessions without inverting SHA-256.
3. Cookies are delivered with `HttpOnly` (preventing XSS session extraction) and `SameSite=Lax` (preventing CSRF session transmission on cross-origin state-changing requests).
